# Импорт паков из Telegram через Temporal

Администратор отправляет ZIP в бота, задаёт название и получает экран статуса.
Бот сохраняет архив в MinIO и долговечный запрос в Mongo inbox. Отдельный
`catalog-import-worker` проверяет архив и изображения, загружает объекты и
публикует готовый каталог. Render worker продолжает выполнять генерации в своей
очереди; импорт не занимает его Activity slot.

## Подготовка локального Telegram Bot API

Облачный Bot API ограничивает скачивание файлов ботом. Для ZIP больше 20 MB
профиль `bot` использует отдельный локальный Bot API server. Это транспорт
Telegram, а не HTTP API ядра. Сервер не публикует host ports; бот обращается к
нему только внутри Docker-сети проекта.

Получите application `api_id` и `api_hash` на [my.telegram.org/apps](https://my.telegram.org/apps).
Это отдельные параметры приложения Telegram; BotFather token остаётся в `API_TOKEN`.
Добавьте свои значения в игнорируемый Git файл `infra/.env.prod`:

```dotenv
TELEGRAM_API_ID='значение api_id'
TELEGRAM_API_HASH='значение api_hash'
```

Эти значения не генерируются setup и не должны попадать в Git или публичные
логи. Если их нет, конфигурация Compose без профиля бота по-прежнему доступна,
а запуск `telegram-bot-api` завершится понятной ошибкой до старта сервера.

Если бот ранее работал через `api.telegram.org`, остановите прежний polling и
выполните явный `logOut` облачного Bot API перед переносом. Это операция над
реальным ботом; setup и запуск Compose её автоматически не вызывают. Порядок
переноса описан в [официальной инструкции Telegram](https://github.com/tdlib/telegram-bot-api#moving-a-bot-to-a-local-server).

После остановки прежнего polling явная команда переноса читает token из
выбранного env-файла и не печатает его:

```powershell
py -3.12 infra/telegram_api.py --env-file infra/.env.prod --logout-cloud
```

Обновите проектное окружение, сохранив существующие credentials и data root:

```powershell
Set-Location D:\Projects\IMagerBOT-1
py -3.12 infra/setup.py --production
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yaml --profile bot up -d --build
```

Для новой установки можно явно выбрать data root на E:

```powershell
py -3.12 infra/setup.py --production --data-root E:/IMagerBOT-1-runtime/data/prod
```

## Использование в боте

1. Постоянный или назначенный администратор открывает `/import_pack` либо
   кнопку загрузки пака в административном разделе библиотек.
2. Отправляет ZIP как документ. Бот проверяет расширение и размер, затем просит
   название. Загружать ZIP как фото не нужно.
3. Вводит отображаемое название. Внутренний ID создаётся автоматически; название
   не используется как путь файла или ключ извлечения архива.
4. Получает экран статуса. Кнопки «Обновить статус» и «Мои импорты»
   показывают очередь, этап обработки, прогресс, результат либо причину отказа.
5. После успешного импорта фоновая проекция автоматически добавляет пак в
   список библиотек бота, обычно в течение пяти секунд. Обновление статуса
   также синхронизирует его сразу. Пересборка или перезапуск worker не нужны.

Роль администратора проверяется у сообщений, кнопок и перед записью запроса.
Обычный пользователь не может запустить импорт или прочитать чужой импорт.
Прежние клавиатуры защищены общим view token, владельцем и revision экрана.
`/cancel` завершает ещё не принятый ввод; принятый импорт выполняется независимо
от диалога и переживает рестарт бота.

Импорт создаёт новую библиотеку. Он не перезаписывает произвольный существующий
пак по введённому названию. Повтор того же сообщения/задания использует прежний
ID и снимок запроса. Настройки повтора и ссылки на архив видны в Temporal UI;
сами байты ZIP в историю Temporal не передаются.

## Проверка архива и ограничения

Параметры находятся в `[pack_import]` файла `config/imager.toml`:

| Ограничение | Значение по умолчанию |
| --- | --- |
| ZIP через Local Bot API | 256 MB |
| ZIP через облачный Bot API при отдельном локальном запуске Python | 20 MB |
| Сумма распакованных файлов | 512 MB |
| Один распакованный файл | 64 MB |
| Записи ZIP, включая каталоги и метаданные | 10000 |
| Центральный каталог ZIP | 16 MB |
| Глубина каталогов / длина пути | 16 / 1024 байта |
| Максимальная степень ZIP-сжатия | 100 |
| Одновременно ожидающие импорты | 2 на администратора, 4 суммарно |

ZIP проверяется до публикации каталога. Запрещены абсолютные пути и `..`,
backslashes и drive prefixes, ссылки и специальные файлы, шифрование,
неподдерживаемые методы сжатия, дубли и конфликтующие пути. Число записей и
границы центрального каталога проверяются до создания объектов `ZipInfo`.
Извлечение выполняется потоком с проверкой реального объёма и CRC, без extractall.

Поддерживаются ZIP_STORED и ZIP_DEFLATED. Изображения во вложенных папках
объединяются в один пак; им присваиваются безопасные временные имена.
Вложенные архивы и другие не-image файлы отклоняются. Настроенные служебные
метаданные `.DS_Store`, `Thumbs.db` и `__MACOSX` не извлекаются.

Каждое изображение дополнительно проходит существующую проверку ядра по
формату, размеру и другим предметным пределам. Перед загрузкой и распаковкой
проверяется запас свободного диска, включая резерв 3 GB для параллельных
транспортных копий и рабочие файлы. В памяти обрабатывается одно изображение,
лимит контейнера импортёра — 1 GB.

## Контейнеры и хранение

`catalog-import-worker` использует очередь `pack_import.task_queue`, по умолчанию
`imager-catalog-import`, и отдельный ThreadPoolExecutor с одним Activity slot.
Production worker подключается к Temporal через уже настроенный mTLS. Общий
диспетчер доставляет отдельный import outbox; рендеринг и импорт имеют разные
workflow types и коллекции заданий.

Setup создаёт собственные пути внутри data root:

- `IMAGER_IMPORT_SCRATCH_PATH`: скачанный ZIP и распакованные изображения worker.
- `IMAGER_BOT_API_DATA_PATH`: транспортный кеш и состояние Local Bot API.
- `IMAGER_BOT_API_TEMP_PATH`: временные файлы сервера Bot API.
- `IMAGER_BOT_SCRATCH_PATH`: временные файлы фотографий и загрузок через облачный Bot API.

Только бот получает read-only mount кеша Bot API по тому же пути, который
возвращается методом getFile. ZIP из Local Bot API загружается в MinIO прямо
из этого каталога, без временной копии в процессе бота. Передача использует
один открытый файловый дескриптор: проверяются фактический размер, ZIP-заголовок
и SHA-256; контрольная сумма повторно считается по байтам, переданным MinIO.
Изменение, рост или обрезание файла прерывает передачу до завершения объекта.
При облачном Bot API сохраняется ограниченная временная загрузка.
Ядро и оба типа worker не монтируют этот кеш:
они получают только MinIO ObjectRef. Для рабочего окружения существующий data
root остаётся на E; setup не переносит его на C.

Оригиналы изображений и manifest имеют неизменяемые content-addressed ключи в
MinIO. Пак появляется в реестре только после полной проверки и загрузки.
Lease и токен публикации запрещают устаревшему исполнителю заменить результат
нового запуска. Ошибка не публикует частично собранный каталог.

Сумма memory limits production-сервисов с одним render worker, одним import
worker, Bot API и ботом — 5.112 GB; это верхние лимиты, без учёта Docker/OS.
Дополнительный worker каждого типа добавляет лимит 1 GB. Учитывайте также место
в MinIO, транспортном кеше Telegram и временных каталогах.

## Интеграционная проверка

Опциональная фикстура находится в
`imager/tests/integration/catalog-import.compose.yaml`, контроллер — в
`smoke_catalog_import.py` рядом с ней. Она использует отдельные MongoDB, MinIO,
Temporal dev server и import worker без production environment и Telegram.

Проверен реальный импорт ZIP размером 25219990 байт с восемью PNG, больше
облачного лимита 20 MB. Activity выполнил отдельный контейнер. Проверены
manifest и изображения MinIO, отображаемое название, итоговый прогресс,
идемпотентный повтор и отказ архива с `../escape.png` без публикации каталога.
На этом тесте пик cgroup памяти import worker составил 104538112 байт;
перезапусков и OOM не было.
