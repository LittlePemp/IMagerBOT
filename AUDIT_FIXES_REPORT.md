# Исправления независимого аудита

Дата: 24 ноября 2026 года. Ветка: `codex/temporal-minio`.

Проверенный базовый коммит: `89721bd1e7ec83781a71a89988b56ec837123a4f`.
Исходный отчёт Claude сохранён отдельно: [FIXES_REPORT.md](FIXES_REPORT.md).
Этот документ описывает итоговые исправления и их проверку.

## Удаление результата после неопределённой записи MongoDB — P1

`RenderActivities` больше не считает отсутствие `result` после ошибки
`complete()` доказательством того, что запись не состоялась. При живом
собственном execution token, неизвестном владельце или отсутствии документа
JPEG сохраняется. Удаление допустимо только для точного ключа этой попытки,
когда job уже терминален либо право исполнения перешло другому владельцу.
Канонические результаты и существующие source/result-ссылки других jobs
сохраняются.

Проверка воспроизводит поздний commit после `NetworkTimeout`: JPEG остаётся,
а повтор Activity возвращает сохранённый результат без повторного рендера.

Файлы: `imager/src/presentation/temporal/activities.py`,
`imager/src/infrastructure/jobs/storage_hygiene.py`.

## Гонка загрузки исходника и janitor — P1

Загрузка, приём запроса и очистка используют общий `SourceLifecycle` с
блокировкой по job ID. Janitor повторно проверяет точные ссылки из admission
и core jobs; новый `stat_object` проверяет возраст текущего объекта, а не
только устаревший результат listing. Отмена janitor дожидается завершения
запущенного синхронного DELETE перед освобождением блокировки.

Дополнительная защита закрывает неопределённый S3 DELETE и перезапуск процесса:
каждый PUT получает собственный случайный upload token. Ключ нового исходника:

```text
uploads/{job_id}/attempts/{upload_token}/{sha256}.jpg
```

Запоздалое удаление прежнего ключа физически не может затронуть новую загрузку.
Job ID, fingerprint принятого запроса и защита от повторного допуска сохраняются.
При наличии квитанции повтор возвращается до новой загрузки.

Старые hash-only ключи и исторические `source.bin`/`source.jpg` остаются читаемыми
и очищаемыми. Общая проверка владения используется retention и просмотром
исходников администратором. Старые непринятые попытки очищаются по конкретному
ключу, даже если другой исходник того же job уже принят.

Проверены оба порядка загрузки и удаления, отмена ожидающего, повторная отмена
выполняющегося DELETE, неопределённый admission, свежий объект за старым listing
и удаление неиспользуемой попытки с сохранением принятой.

Файлы: `telegram_bot/src/application/source_lifecycle.py`,
`telegram_bot/src/application/generation.py`,
`telegram_bot/src/infrastructure/services/storage_janitor.py`,
`telegram_bot/src/infrastructure/services/object_storage/minio_storage.py`,
`telegram_bot/src/infrastructure/services/imager_service/imager_service.py`,
`imager_contracts/storage_keys.py`,
`imager/src/infrastructure/jobs/image_retention.py`.

## Параллельное чтение кэша Local Bot API — P2

Перед `getFile` регистрируется незавершённое получение пути; затем закрепляется
конкретный файл до окончания чтения и передачи в MinIO. Немедленное удаление
откладывается до последнего читателя. Возрастная очистка использует тот же
thread-safe реестр, проверяет активных читателей, тип и возраст под общей
блокировкой. Ошибка или отмена получения пути освобождает регистрацию.

Фото, статические стикеры, превью и ZIP используют общий механизм. ZIP передаётся
из общего каталога напрямую, без второй полной временной копии. Ошибки удаления
логируются без пути, содержащего токен Telegram.

Проверены два параллельных читателя фото/стикера и ZIP, очистка во время
ожидания `getFile` и во время чтения, отмена и ошибка запроса.

Файлы: `imager_contracts/scratch.py`,
`telegram_bot/src/infrastructure/services/telegram_files.py`,
`telegram_bot/src/commands/image_generation/upload.py`,
`telegram_bot/src/commands/admin_panel/pack_import/handlers.py`.

## Удержание декодированных массивов и неверный отчёт импорта — P2/P3

Обработка одного изображения вынесена в отдельную функцию, которая возвращает
только метаданные. Ссылки `decoded`, `validation.value` и нормализованный массив
освобождаются до следующего файла, включая все ветки пропуска. CLI сохраняет
строгий режим, импорт ZIP — режим пропуска некорректных изображений.

Дубликаты считаются при повторении SHA-256 отдельным счётчиком. Повреждённые
файлы больше не увеличивают `duplicate_files`.

Проверены настоящие небольшие float64 RGBA TIFF и время жизни массивов через
weakref, неверная геометрия, повреждённый файл, повторный SHA и строгий режим.
Большие изображения для искусственного OOM не создавались.

Файл: `imager/src/infrastructure/object_storage/catalog.py`.

## Ограничение квитанций при возврате квоты — P2

Успешная дневная квота обычного пользователя остаётся равной пяти генерациям.
Ошибки ядра возвращают использованную единицу идемпотентно. Отдельно введён
лимит 64 принятых попыток в московские сутки, включая возвращённые неудачные
попытки. Он ограничивает размер дневного BSON-документа и поток повторов при
продолжительных сбоях. Проверка выполняется до загрузки и атомарно при записи.

Администраторы сохраняют неограниченные попытки и отдельный документ на
изображение. Квитанции не перемещаются и не обрезаются: атомарность квоты,
admission и outbox, защита от дублей и обработка потерянного ACK сохранены.
Старые переполненные корзины доступны для повторов и публикации, но не принимают
новые обычные попытки в этот день.

Лимит централизован в `bot.max_daily_admissions = 64`; конфигурация проверяет
диапазон от обычной дневной квоты до предельного бюджета 256 квитанций.
Пользователь получает отдельную ошибку лимита попыток.

Проверены 64 цикла допуска/возврата, отказ следующего, повтор уже принятого
после лимита, конкуренция за последний слот, legacy-переполнение и отсутствие
этого ограничения у администратора.

Файл: `telegram_bot/src/infrastructure/data/repositories/admission_repository.py`.

## Очистка незавершённых outbox и проекций — P2

TTL по `created_at` заменён абсолютным `expires_at` с TTL 0. При старте снимается
только известный старый TTL-индекс. Незавершённые публикации, уведомления и
неизвестные состояния уведомления не имеют срока удаления. Закрытая корзина
получает 90 дней хранения; новый допуск, повтор публикации и повтор после
явного FloodWait атомарно снимают срок удаления. Закрытым legacy-корзинам
миграция назначает новый срок, не удаляя их сразу.

Core purge сохраняет Telegram job до подтверждённого `synced` проекции истории
и возврата квоты. Для артефактов требуется фактический `deleted`;
`unmanaged` больше не считается доказательством удаления файла.

Проверены pending/claimed/отсутствующая проекция, закрытая проекция,
неизвестное состояние уведомления, миграция индекса и повторное открытие корзины.

## Границы проверки и обновление

- Полный цикл через настоящие Telegram и Local Bot API не запускался.
- Не запускался полный Temporal Compose; поздняя запись Mongo проверена
  управляемым воспроизведением Activity, не сетевым fault injection.
- Реестр кэша и SourceLifecycle рассчитаны на один polling-процесс бота.
  Исполнители ядра по-прежнему масштабируются отдельно. Неизменяемые source
  keys дополнительно защищают от запоздалого DELETE прежнего процесса.
- Поддерживаются существующие ссылки других jobs; произвольному внешнему
  writer, одновременно создающему новые ссылки на старые объекты, нужен
  отдельный протокол закрепления файлов.
- Изменения не восстанавливают данные, удалённые предыдущей версией.
- При развёртывании сначала обновляется ядро, понимающее новые source keys,
  затем бот. Общая конфигурация и `imager_contracts` должны соответствовать
  версии кода. Индексы admission мигрируют при старте бота.
- Продакшен в рамках этой задачи не обновлялся.
