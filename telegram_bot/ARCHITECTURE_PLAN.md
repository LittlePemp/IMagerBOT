# Архитектура Telegram бота и правила работы

`telegram_bot` управляет диалогом, пользователями, доступом, дневной квотой и доставкой. `imager/` отвечает за расчёт, предметные ограничения изображения, каталог и выполнение в отдельном Temporal worker. Файлы передаются через MinIO, задания и подтверждения — через Mongo inbox/outbox. HTTP, Redis и новые брокеры для бота не добавлялись.

## Постоянные и назначенные администраторы

`TELEGRAM_ADMIN_IDS` — постоянные администраторы, перечисленные через `|`. Все эти ID инициализируются при запуске процесса или контейнера бота. Им нельзя снять роль или поставить блокировку через административный интерфейс. Они остаются администраторами даже при ошибочно изменённой записи Mongo. Пустой список запрещён настройками.

Остальные назначения хранятся в Mongo. AuthenticationMiddleware загружает пользователя для Message и CallbackQuery, AdminFilter и операции записи проверяют актуальные права. Назначение и отзыв действуют сразу. Список из настроек не пополняется администраторами из БД; перезапуск не возвращает отозванную динамическую роль.

Пользователь определяется по telegram_id; username необязателен. Регистрация использует атомарный upsert и уникальный индекс. Административные изменения фиксируют actor_id, target_id, revision и изменённые поля в журнале без тела сообщений.

## Кнопки и навигация

Каждый показ клавиатуры создаёт новый случайный view token. Сервер хранит владельца, chat_id, message_id, срок действия, допустимые действия и выбранные записи. В callback находятся короткие token и индекс. Полные названия и параметры не передаются в Telegram callback_data.

Перед действием проверяются владелец, сообщение, текущий token, срок и состояние FSM. Перерисовка экрана, /menu и /cancel делают прежние кнопки недействительными. При отказе бот отвечает, что экран устарел, без изменения бизнес-данных. Административная команда дополнительно использует target_id и expected_revision из серверного снимка. Запись выполняет явное grant/revoke/ban/unban, а не переключение старого флага.

Для одного polling-процесса включён SimpleEventIsolation. События одного пользователя во время уже выполняющегося действия отсекаются до FSM/БД с ограниченным уведомлением. Поэтому завершение старой загрузки не очищает новый диалог. Исполнители ядра масштабируются независимо от polling-процесса.

FSM хранится в существующей Mongo через PyMongoStorage. Экран истекает через `bot.ui_view_ttl_seconds`; Mongo TTL удаляет просроченный документ диалога. Удалённое состояние не отменяет уже принятые задания. /help показывает справку без изменения текущего ввода; /start, /menu и /cancel завершают ввод и открывают меню. Общий fallback регистрируется последним.

## Дневная квота и защита от перегрузки

Каждому аккаунту, включая администраторов, доступны **5 принятых заданий за календарный день Europe/Moscow**. Сброс происходит в московскую полночь. Поле `bot.regular_user_upload_limit` сохранено для совместимости конфигурации и теперь означает именно дневной лимит всех аккаунтов.

Квота считается по допускам, а не по восстанавливаемой истории. Ошибка уже принятого расчёта не возвращает приём автоматически. Повтор того же Telegram сообщения имеет прежний job_id, возвращает прежнюю квитанцию и не списывает квоту повторно. Новое сообщение с тем же фото считается новым заданием.

Один документ на пользователя и дату содержит used, не более пяти admissions и встроенный outbox. Атомарное изменение одновременно увеличивает used и сохраняет полный закреплённый запрос. Уникальный multikey-индекс admissions.job_id запрещает перенос того же задания в другие сутки. Журналируемый write concern подтверждает сохранение допуска. При потерянном ACK запись перечитывается; неопределённый приём не освобождает слот по таймеру.

При первом обращении за сутки существующие задания Telegram из core inbox за этот московский день учитываются через initial_used. Счётчик вставляется только при создании дневного документа; последующие обращения его не перезаписывают. Сбой проверки БД запрещает новый приём и обрабатывается общим error boundary.

Значения защиты находятся в `config/imager.toml`:

| Ограничение | Значение по умолчанию |
| --- | --- |
| События одного пользователя | 2 в секунду, burst 6 |
| Общие события | 20 в секунду, burst 40 |
| Интервал фотографий одного пользователя | 10 секунд |
| Одновременно обрабатываемые updates | 32 |
| Одновременные загрузки фото | 2 суммарно, одна на пользователя |
| Ожидающие задания | 64 суммарно в bot outbox и core execution |
| Уведомления об ограничении | Не чаще одного за 10 секунд на пользователя, с общим бюджетом |
| Кеш счётчиков ограничения | До 10000 пользователей, очистка неактивных |

Дешёвый rate limiter включается до Mongo FSM и проверки профиля. Вход разрешён только в личных чатах. Общий локальный admission/publication lock не позволяет новому допуску обойти лимит очереди между подсчётом и публикацией. Он рассчитан на один polling-процесс; второй бот с тем же токеном не является способом масштабирования.

Внешние Telegram updates получает инфраструктура Telegram. Описанные ограничения защищают ресурсы приложения от спама и перегрузки. Скачивание ограничено фактическим числом записанных байтов, включая случай отсутствующего или неверного file_size. Лимит исходного файла и лимиты изображения принадлежат общей конфигурации и ядру.

## Приём и выполнение задания

1. Бот ищет существующую квитанцию и прежнее core-задание по детерминированному job_id, проверяет владельца.
2. Проверяет пользователя, выбранную библиотеку, существование пресетов, дневной остаток и очередь до скачивания.
3. Ограниченно скачивает фото во временный файл и загружает его в MinIO. Временные файлы удаляются при выходе из контекста, включая отмену.
4. Повторно проверяет правила, закрепляет параметры, manifest, seed, execution policy и workflow ID. Перед допуском снова проверяет политику и очередь.
5. Атомарно сохраняет дневную квоту и полный запрос в bot outbox. После подтверждения отвечает «принято». Это означает долговечный допуск бота, а не уже начавшийся расчёт.
6. AdmissionDispatcher публикует тот же документ в core inbox через setOnInsert и проверку fingerprint. Он использует lease, продление и CAS-токен. Тайм-аут или рестарт приводят к повтору того же запроса, без перечитывания изменяемых параметров.
7. Диспетчер ядра запускает Temporal; отдельный worker выполняет синхронную сборку. Бот получает completion outbox.

Между Mongo бота и ядра нет распределённой транзакции. Сохранность обеспечивают локальный атомарный допуск, outbox и идемпотентная повторная публикация. Изменение TOML или каталога после приёма не изменяет закреплённый запрос.

## Хранение

Общий mutable self.session и фиктивные commit/rollback удалены. MongoRepositories — bundle репозиториев без состояния запроса, создаваемый в bootstrap. Совместимые async with и имя MongoUnitOfWork остались временными алиасами без обещания транзакции; активные обработчики ими не пользуются.

Пул AsyncMongoClient принадлежит bootstrap и используется репозиториями и FSM. Mongo-транспорт ядра пока использует отдельный синхронный клиент в адаптере через asyncio.to_thread; MinIO также остаётся синхронным адаптером. Синхронные вызовы не блокируют event loop бота. Записи используют атомарные операции одного документа, unique indexes и CAS вместо общей mutable сессии.

При запуске создаются индексы идентичности пользователя, пресетов, библиотек, истории, admissions и TTL диалогов. Найденные старые дубли не удаляются автоматически: запуск должен сообщить о конфликте, чтобы сохранить роли и данные. Ошибка БД отличается от отсутствия записи и не превращается в нулевую квоту.

## Пресеты и библиотеки

Числовой пресет проходит проверки конечности, целочисленности и диапазона при создании и сохранении. NaN, Infinity, дроби и выход за диапазон отклоняются с понятным ответом. Некорректные старые пресеты скрыты от пользовательского выбора, но видны администратору для удаления. Пользователь выбирает серверный снимок; перед приёмом сверяется существование прежнего имени и значения.

Редактируемые пресеты и отображаемые имена продолжают жить в Mongo, поэтому их изменение не требует redeploy. Жёсткие пределы расчёта задаются ядром; бот выполняет раннюю проверку и не заменяет окончательную проверку ядра оценкой размера JPEG.

Ручной статус библиотеки отделён от available_in_core. Администратор видит и отключённые библиотеки и может включить их обратно. Исчезновение и возвращение каталога не меняет ручной статус. Переименование меняет только отображаемое имя, проверяет непустое значение и длину; записи используют revision CAS. Отключённая после выбора библиотека не проходит проверку приёма. Уже принятые задания продолжают использовать закреплённый manifest.

Кнопка синхронизации обновляет список каталогов ядра. Для нового пака администратор выбирает «Загрузить ZIP-пак» или `/import_pack`, отправляет архив и задаёт название. Бот сохраняет архив в MinIO и долговечный запрос в отдельном inbox; отдельный Temporal worker проверяет ZIP и изображения и публикует каталог. Списки параметров и библиотек разбиты на страницы.

Статус импорта показывает фазу, прогресс и безопасное описание ошибки; доступны последние импорты администратора. Фоновая проекция добавляет успешно опубликованный пак в библиотеки без обязательного клика по статусу. Это создание нового пака с внутренним стабильным ID; обновление существующего по ID пока остаётся CLI-операцией.

Большие ZIP передаются через отдельный Local Bot API Server. Его кеш находится на E и доступен боту только для чтения; ZIP загружается в MinIO напрямую из кеша без временной копии бота. Фактический размер и SHA-256 проверяются на одном открытом дескрипторе, включая байты, передаваемые MinIO. Ядро читает только MinIO. Начальные лимиты: ZIP 256 MB, распаковка 512 MB, до 10000 записей, один импорт на отдельный worker с бюджетом 1 GB. Пути, ссылки, шифрование, CRC, действительный размер распаковки и коэффициент сжатия проверяются до публикации. [Развёртывание и сценарий](../infra/PACK_IMPORT.md).

## Доставка и восстановление

Notifier отправляет результат независимо от состояния истории. Отдельный цикл с собственным lease и backoff восстанавливает проекцию истории из канонического задания, включая случай недоступной bot Mongo. Его ошибки не расходуют бюджет Telegram-доставки.

TelegramRetryAfter переносит следующую попытку на retry_after плюс настроенный запас и возвращает попытку в бюджет. Сетевые ошибки получают ограниченный backoff с jitter. Постоянный запрет Telegram или повреждённый контракт отмечается отдельно. Пользователь получает безопасное описание и job_id; техническая причина и стек сохраняются в журнале без локальных переменных и полного Update.

Пользователь видит состояние своего изображения без номеров, UUID и понятия задания. «Моё изображение» в меню и `/status` открывают последний подтверждённый приём этого пользователя; если сохранённого bot admission нет, проверяется прежняя запись ядра. Кнопки статуса и повторной отправки используют внутренние ID только в серверной навигации. `/retry_delivery` без номера и кнопка повтора доступны владельцу готового результата с неуспешной доставкой. CAS изменяет только failed completion outbox в pending. Повтор не запускает workflow, не меняет результат и не списывает дневную квоту. Повтор команды не сбрасывает уже ожидающую, выполняющуюся или завершённую доставку. Технические ID также исключены из подписей, ошибок и имён отправляемых файлов; они остаются в журналах и инфраструктуре.

Доставка остаётся «как минимум один раз»: остановка между успешным sendDocument и Mongo ACK может дать повтор сообщения. Telegram и Mongo не участвуют в общей транзакции.

## Структура реализации

- `main.py`: composition root, lifecycle, регистрация middleware и маршрутов; импорт не создаёт клиентов и не запускает polling.
- `commands/image_generation/image_generation_handler.py`: регистрация маршрутов.
- `commands/image_generation/wizard.py`: выбор режима, пресетов, ручной ввод, библиотеки и навигация.
- `commands/image_generation/upload.py`: ограниченный Telegram source adapter и небольшой photo handler.
- `application/generation.py`: проверка политики и SubmitGeneration.
- `application/admission.py`: повторная публикация долговечного допуска.
- `commands/admin_panel/ui.py`: короткие типизированные административные команды и серверные snapshots.
- `commands/jobs.py`: собственный статус и повтор доставки.
- `utils/navigation.py`: владелец, текущий экран, token, срок действия.
- `utils/middlewares/abuse_control.py`: ограничения событий и загрузок.
- `infrastructure/data/repositories/admission_repository.py`: дневная квота и атомарный outbox.
- `infrastructure/services/imager_service/`: транспорт ядра, доставка и восстановление истории.

## Проверки и дальнейшая работа

Offline-проверки используют настоящий Dispatcher/FSM и fake Telegram session. Они покрывают роли, старые кнопки, сценарии выбора параметров, навигацию, ошибки БД, квоту, source transfer, неизменяемый запрос, lease, FloodWait, статус и повтор доставки. Ядро проверяется отдельным набором регрессионных тестов.

`tests/integration/smoke_mongo_admission.py` отдельно проверен на MongoDB 7.0.45 в новом временном контейнере с памятью 384 MiB. Шесть конкурентных допусков дали пять успешных, проверены unique multikey между сутками, rollback счётчика, миграция, продление lease и отклонение старого токена. Production data и Telegram не использовались.

Перезапуск больше не удаляет ожидающие Telegram updates намеренно. Стандартный concurrent polling всё же подтверждает получение Update отдельно от допуска бизнес-команды. Для гарантии сохранности до приёма нужен отдельный Telegram update inbox с управляемым offset. Сейчас долговечность гарантируется после подтверждённого допуска.

Дальше остаются автоматизированная уборка неподтверждённых MinIO uploads с проверкой ссылок, политика хранения готовых результатов и дневных receipts, а также метрики зависших допусков и доставок. Принятые/pending sources удалять по общему возрасту нельзя. Для нескольких интерфейсных процессов потребуется распределённая координация ограничений; исполнители ядра уже масштабируются отдельно.
